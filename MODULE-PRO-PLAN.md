### Buying & Procurement — 4.8/10

**Verdict.** Not professional grade today — it is a clean request-logging skeleton with two visibly dead buttons, a demo that shows "—" for every naira figure, and no purchase order to actually send a supplier; the security layer is the only genuinely strong part. Roughly 2-3 focused engineering weeks from a paying Lagos SME calling it professional.

**Top gaps.**

- DEAD BUTTON — request Edit does nothing. ProcurementApp.jsx L183 calls setEditReq(r), but `editReq` is never rendered anywhere (only `reqModal` and `vendorModal` are, L217-218). A user clicks Edit on their pending request and the UI does absolutely nothing, silently. Same class of dead state: `editVendor` (L109) and `openVendor` (L110, comment says 'vendor id with details row expanded' — a feature never built).
- NO VENDOR EDITING AT ALL. The vendors table (L203-211) renders only a Delete button. VendorModal's entire edit branch, P.editVendor, and the PATCH /procurement/vendors route are unreachable code. Typo a supplier's phone number and your only recourse is delete-and-recreate, which nulls the vendor_id on every historical request (on delete set null).
- DEMO SHOWS NO MONEY. demo.js seeds purchaseRequests (L893-894) and creates them (L917) with no `total_cost` field, but the table renders P.money(r.total_cost) (L172) and money() returns '—' for null. In the prospect-facing /try/procurement demo — the sales surface — the Total column is '—' on every single row, in a suite whose entire pitch is 'money is not spent without a yes'. Live Supabase has total_cost as a generated column, so this never shows up in your own testing.
- VAT RATE IS A NAIRA-DESTROYING TRAP. The field is a raw decimal input labelled 'VAT rate' defaulting to 0.075 (L87). A Nigerian SME user types 7.5 (the rate they know) and the total becomes qty x cost x 8.5 — an 850% total, silently persisted. There is no clamp in the UI, no CHECK constraint on vat_rate in procurement.sql, and total_cost is a generated column so the bad number is baked in.
- SILENT-SUCCESS ON A DENIED DELETE. supabaseApi L2147 does .delete().eq('id',...) with no .select(). Under RLS, a non-manager deleting their own already-approved request matches zero rows and Postgrest returns NO error — so the client flashes 'Request deleted.', reloads, and the row is still sitting there. Worse, the Delete button is rendered for every row to every user regardless of role or status (L184), so this is the default path for staff.
- THE CONFIRM DIALOG LIES. removeRequest (L128) says '...and its approval history will be permanently removed.' There is no approval-history table anywhere in procurement.sql — only vendors and purchase_requests. Nothing is being removed because nothing is being recorded.

### Time & Attendance — 5.5/10

**Verdict.** Craft-level UI and a genuinely differentiated universal punch lane sitting on a payroll-grade data layer that any employee can forge from the browser console — impressive for a demo, roughly 3-5 focused weeks (self-write RLS, absence board, multi-site fence, pagination, forgot-to-clock-out repair) from what a 50-field-staff customer would call professional.

**Top gaps.**

- SECURITY, headline: supabase/attendance.sql:53 grants policy "attendance_write" FOR ALL to `employee_id = auth.uid()`. Every staff member holds a real JWT and the anon key is in the bundle, so any employee can `supabase.from('attendance_records').insert({clock_in_at:'07:00', is_late:false, ...})` or UPDATE their own clock_out_at from their sofa. This bypasses attendance_clock_in() entirely — the geofence, phone_enabled, the one-open-shift rule and the is_late/late_minutes stamping are all advisory. Everything the recent geofence hardening bought is undone by the table policy behind it.
- SECURITY: employees can also DELETE their own rows under the same policy — a late clock-in can be erased with no trace, and there is no audit/history table for attendance_records at all. Manager pencil edits are equally untracked (no edited_by/edited_at/previous_value), so a disputed payroll deduction has no evidence trail.
- SECURITY: attendance_device_map RLS select is `same_org(org_id)` only (attendance_payroll.sql:81) — any employee in the org can read the full PIN-to-person map, which is the lookup table an insider needs to forge punches if a device key ever leaks.
- SECURITY: /api/punch has no rate limiting, no per-device request cap, no key rotation and no last-IP record. A leaked device key forges unlimited punches for that org until a manager notices and deletes the device (which is destructive — there is no rotate).
- BUG, headline: forgot-to-clock-out corrupts the next day. Auto-close only fires at 20h of age (attendance_phase1.sql:43). Clock in Mon 08:00, forget to clock out; Tue 08:00 is only 24h — the watchdog may have closed it, but if the person clocks out manually first they stamp a 24-hour shift with auto_closed=false, i.e. unflagged, payable, provisional-looking-real. On the wall-device lane it is worse: attendance_apply_punch with direction 'auto' closes the stale open shift at Tue 08:00 (24h) and does NOT open Tuesday's shift, so the person is absent all Tuesday and paid for a fictional 24h Monday.
- BUG: no debounce on wall punches. A single-reader terminal where someone taps twice in five seconds produces open-then-close — a 0.0h shift, and the person is 'clocked out' for the rest of the day. attendance_apply_punch has no minimum-interval / anti-passback window.
- _(+20 more in the raw run)_

**Plan (designer draft — not yet board-cut).**

1. Close the self-write hole in attendance_records. Replace the FOR ALL policy in supabase/attendance.sql:53 with: SELECT for `is_attendance_manager() OR employee_id = auth.uid()`; UPDATE/DELETE for managers only; and NO client INSERT policy at all — clock-in/out already run through SECURITY DEFINER RPCs, so nothing legitimate breaks. Add a BEFORE UPDATE trigger that rejects changes to is_late/late_minutes/source/clock_in_lat/lng from a non-definer context. Ship test/attendance_self_write_denied.mjs alongside it, running as a real employee role like support_write_denial.mjs does, asserting insert/update/delete all fail.
2. Add an attendance_record_edits audit table (record_id, edited_by, edited_at, field, old_value, new_value) written by a trigger on attendance_records UPDATE, and surface it as a 'Change history' section in EditShiftModal. Payroll input with no evidence trail is the thing a demanding customer's accountant rejects first.
3. Fix the forgot-to-clock-out path in both lanes. In attendance_clock_out(): if now() - clock_in_at exceeds a threshold (settings.work_close of the clock-in day, or 12h), close at the scheduled close, set auto_closed = true, and return a flag so the UI says 'We closed yesterday's shift at 17:00 — a manager must confirm the hours' before opening today's. In attendance_apply_punch(): when direction 'auto' finds an open shift older than that threshold, close it as auto_closed AND open a new shift at p_at in the same call, instead of silently swallowing the day.
4. Add a debounce to attendance_apply_punch: ignore any punch within N seconds (settings column, default 60) of the same employee's last punch, and record it in attendance_device_punches with error='debounced'. One double-tap at a wall reader currently costs a person their whole day's hours.
5. Delete DAY_START_HOUR from attendanceApi.js and drive every 'Late' pill and the Late KPI from the record's own is_late / late_minutes columns (already stamped correctly against each person's shift + grace). Change the KPI label from 'Late today (after 09:00)' to 'Late today' with the person's own shift in the row tooltip, and remove the 'This will become an org setting' footnote — the setting already exists.
6. Paginate and window every attendance read. Change GET /attendance/records to take from/to and .range(), and have TimesheetView request only the week it is showing and TodayView only today; make GET /attendance/mine default to the last 60 days with a 'Load older' control. Without this the Timesheet is provably wrong from month two at 50 staff because of PostgREST's 1000-row cap.
7. Rewrite the /api/punch loop to be batched: one .insert() of all raw punches with ignoreDuplicates, one .in() select of the whole PIN map, then a single set-returning RPC attendance_apply_punch_batch(jsonb) that loops server-side inside Postgres, then one bulk status update. Set maxDuration in client/vercel.json. Target: a 500-punch batch in under 3 seconds instead of ~1600 sequential round trips that currently time out.
8. Build the absence board — the missing headline screen. Add a manager view that joins today's expected roster (attendance_shift_assignments where today is in shift.days, else settings.working_days) against actual clock-ins, minus anyone with an approved leave request, and renders three groups: On shift, Late, Not arrived. Add 'Not arrived' as a fourth KPI. This is the single change that most moves this from a log into a workforce tool.

## Question 15 — where does the Compliance Calendar belong?

**Recommendation: leave the engine standalone, and surface it as a read-only panel inside HR and inside Finance. Do not move it into HR.**

The deciding fact is that the nine rules split across two different owners, almost evenly:

| Payroll/HR owns | Finance/company secretary owns |
|---|---|
| PAYE remittance, Pension (PenCom/PFA), NHF, NSITF, PAYE annual return | VAT, WHT, Companies Income Tax, CAC annual returns |

Nobody owns the whole calendar, so "put it in HR" quietly means your accountant can only see the VAT and CIT deadlines by holding the HR suite — and the HR suite is the most sensitive one in the product (the full staff directory, personal data, employee documents). You would be handing out the crown jewels to display a checklist. That is the real argument, and it is a security argument, not a taste one.

So: one engine, two embedded surfaces. Payroll-linked deadlines appear on HR next to the statutory meter; tax and company deadlines appear on Finance. Same table, same API, zero duplicated code, and the standalone tile stays for whoever wants the full view.

**Separate decision you should make anyway: it is currently billed as an extra suite.** Today the module is a manual checklist that reads no payroll data — the PAYE card does not know what you actually remitted. Charging an extra suite fee for that is a trust risk with an SME buyer who clicks in once. Two honest options: bundle it free with Payroll, or earn the fee by wiring each monthly rule to the matching payroll run so PAYE/pension/NHF show the real amount due and tick themselves off a recorded remittance reference. The second one turns it into a genuine product; until then I would not defend the line item.
